# ADR-0001: Multi-tenancy με shared schema και cross-company reads

**Κατάσταση:** Αποδεκτό
**Ημερομηνία:** 2026-08-30

## Context

Χρήστης του συστήματος είναι λογιστικό γραφείο που διαχειρίζεται πολλές
επιχειρήσεις-πελάτες. Κάθε επιχείρηση είναι ξεχωριστή νομική οντότητα με δικό
της ΑΦΜ, δικές της σειρές αρίθμησης και δικά της ηλεκτρονικά βιβλία στην ΑΑΔΕ.

Η δουλειά του λογιστή είναι **οριζόντια**: ξεκινά τη μέρα με «τι εκκρεμεί
σήμερα», όχι με «ας δω τι κάνει η εταιρεία Χ». Αν χρειάζεται να μπαίνει σε
κάθε εταιρεία ξεχωριστά για να δει αν υπάρχει νέα εργασία, το εργαλείο είναι
άχρηστο σε χαρτοφυλάκιο 40 πελατών.

Ταυτόχρονα, το να δει ο λογιστής δεδομένα εταιρείας που δεν του ανήκει είναι
**διαρροή φορολογικών δεδομένων τρίτου**, όχι bug εμφάνισης.

## Options

**Α. Database per tenant.** Πλήρης απομόνωση, αλλά 40 βάσεις να συντηρούνται
και migrations να τρέχουν 40 φορές. Cross-company queries πρακτικά αδύνατα.

**Β. Shared database, schema per tenant.** Λιγότερο βαρύ, αλλά η Postgres
απαιτεί αλλαγή search_path ανά request και τα cross-company queries παραμένουν
δύσκολα.

**Γ. Shared database, shared schema με `company_id`.** Μία βάση, ένα schema,
φιλτράρισμα σε επίπεδο εφαρμογής.

Ορθογώνια σε αυτό, το ερώτημα του default view:

**Γ1. Active company.** Ο χρήστης «μπαίνει» σε μία εταιρεία, όλα φιλτράρονται
σε αυτήν.

**Γ2. Cross-company.** Ο χρήστης βλέπει όλες τις εταιρείες του ταυτόχρονα,
με προαιρετικό φίλτρο.

## Decision

**Γ + Γ2:** shared schema με `company_id`, φιλτράρισμα μέσω **Eloquent Global
Scope**, και cross-company reads ως προεπιλογή.

Το φιλτράρισμα γίνεται σε **δύο ξεχωριστά επίπεδα**:

1. **Security boundary** — Global Scope, πάντα ενεργό, φιλτράρει στις εταιρείες
   που ο χρήστης δικαιούται (`User::accessibleCompanyIds()`). Δεν
   απενεργοποιείται.
2. **Context filter** — προαιρετικό `?company_id=` στο query string. Απλή
   διευκόλυνση, χωρίς ρόλο ασφαλείας.

Η πολιτική πρόσβασης ζει **αποκλειστικά** στη `User::accessibleCompanyIds()`.
Σήμερα επιστρέφει όλες τις εταιρείες (single-firm deployment). Αν αύριο μπει
ανάθεση ανά λογιστή, αλλάζει μόνο αυτή η μέθοδος.

## Consequences

**Κερδίζουμε:** ένα schema και ένα set migrations· cross-company queries χωρίς
κόστος· ένα σημείο αλλαγής για την πολιτική πρόσβασης.

**Πληρώνουμε:**

- Κάθε write path πρέπει να επικυρώνει ρητά το `company_id`. Το Global Scope
  προστατεύει τα reads, όχι τα writes: `company_id: 999` στο payload θα
  δημιουργούσε εγγραφή σε ξένη εταιρεία. Λύνεται με
  `Rule::in($user->accessibleCompanyIds())` σε κάθε Form Request.

- Οι σχέσεις μεταξύ οντοτήτων πρέπει να ελέγχονται για **ίδια εταιρεία**.
  Ο λογιστής βλέπει πελάτες πολλών εταιρειών· ένα λάθος `customer_id` θα
  εξέδιδε τιμολόγιο της εταιρείας Χ σε πελάτη της Ψ, και το Global Scope δεν
  το εμποδίζει γιατί και οι δύο είναι εντός του επιτρεπτού συνόλου.

- Κάθε λίστα πρέπει να δείχνει σε ποια εταιρεία ανήκει η κάθε γραμμή.

- Η απομόνωση εξαρτάται από τον κώδικα, όχι από τη βάση. Ένα
  `withoutGlobalScopes()` την παρακάμπτει. Καλύπτεται με tests.
